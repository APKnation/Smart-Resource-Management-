1 · What this project is

The repository is mid-transition from an E-Resources Management System (document/file sharing portal — package name is still e_resource) into a Hospital Resource Management System (HRMS) — a multi-tenant, role-gated inventory, procurement and asset platform. Both subsystems coexist in one app.

Read the README warning

The project explicitly states it is not production-ready. It is a working prototype whose security boundary is real (Postgres RLS + SECURITY DEFINER functions), but whose operational coverage is partial.

Key architectural decision

Authorization is enforced server-side, not in Dart. Stock balances and movement rows have REVOKE INSERT, UPDATE, DELETE from authenticated; they can only change through record_stock_movement() and hrms_transfer_stock(). The client's role checks exist only to show/hide UI — the database is the authority.

6 · Tenancy + RBAC — the security spine

Every HRMS table carries a hospital_id. A user's access to a hospital is a row in hrms_memberships — and a user may hold several memberships (different hospitals, different roles, optionally scoped to a department) at once.

6.1 The single gatekeeper function

hrms_has_membership(p_hospital_id uuid, p_roles hrms_membership_role[] DEFAULT NULL) → boolean
LANGUAGE sql STABLE SECURITY DEFINER · SET search_path = public, pg_temp 
exists (select 1 from hrms_memberships m
  where m.user_id = auth.uid() and m.hospital_id = p_hospital_id
    and m.is_active and (p_roles is null or m.role = any(p_roles)))

Runs as the function owner, so a user can test membership without SELECT rights on the membership table itself. REVOKE ALL FROM public + GRANT EXECUTE TO authenticated — anon cannot call it. The search_path pinning blocks search-path hijacking.

6.3 Defence in depth — three independent layers

Layer 1 · Dart UI gatingScreens compute _roles from the selected hospital and hide buttons — e.g. _canCreate in workflows_screen.dart:116, _canManageInventory/_canMoveStock in the dashboard.
↓ bypassing this gains nothing
Layer 2 · PostgreSQL privilegesREVOKE INSERT, UPDATE, DELETE ON stock_balances, stock_movements FROM anon, authenticated; stock_transfers is grant-limited to SELECT, INSERT only. Direct tampering is a permission error, not a policy check.
↓
Layer 3 · RLS policies per tableEvery table has ENABLE ROW LEVEL SECURITY plus a "… read …" policy using hrms_has_membership(hospital_id) and a write policy restricted to an explicit role array — with both USING and WITH CHECK, so a row cannot be re-parented into another hospital.

7 · The per-screen HRMS data-fetch pattern

All six HRMS screens repeat the same shape. Understanding it once explains the whole module set.

initState()Instantiate a private HrmsService; set _hospitals = _service.hospitals() as a late Future.
↓
FutureBuilder<List<HrmsHospital>>States: error → error panel (+ Retry); no data → spinner; empty list → "No active hospital membership is assigned to this account."
↓
_hospitalId == null ?Auto-select inside WidgetsBinding.instance.addPostFrameCallback → _select(hospitals.first). Selecting during build is illegal in Flutter, hence the post-frame deferral.
↓
_select(hospital)Sets _hospitalId, caches _roles = hospital.roles (drives every button), and starts _rows = _load(hospitalId) — which first fetches the picker dependencies (departments / warehouses / items / suppliers / assets), then the module list.
↓
Hospital dropdown + list + action buttonsSwitching hospital re-runs _select. After a mutation, screens call setState(() => _rows = _load(_hospitalId!)) — a full re-query, not an optimistic patch.

7.1 Service call shape

HrmsService uses only two Supabase verbs: query-builder chains (.from(t).select(cols).eq('hospital_id', id).order().limit(n)) and .rpc(fn, params: {p_…}) for the privileged operations. Every list read carries an explicit hospital_id filter and a hard limit (100 / 200 / 500) — pagination is not implemented.

Consequence of the per-screen pattern

The selected hospital lives in each screen's private state and is not persisted or shared. Navigating from Inventory to Transfers re-fetches the hospital list and silently resets to hospitals.first. A user with three hospitals must re-pick the tenant on every page. There is no AppState.currentHospitalId.

10 · Module flow: Stock movements — record_stock_movement

The only legal way to change a balance. plpgsql, SECURITY DEFINER, returns the new movement id.

1 · Auth guardIF auth.uid() IS NULL → RAISE 'Authentication required'
↓
2 · Quantity guardNULL or ≤ 0 → 'Quantity must be greater than zero'. Column-level CHECK (quantity > 0) backs this up.
↓
3 · Role gate (kind-dependent)receipt/adjustment/wastage → {hospital_admin, inventory_manager, pharmacist}; everything else → that set plus storekeeper. Failure → 'Not authorized for this hospital operation'.
↓
4 · Batch eligibility + row lockIf p_batch_id given: SELECT … FOR UPDATE requiring, for issue, that NOT is_quarantined and expires_on IS NULL OR expires_on ≥ current_date. Not found → 'Batch not found or unavailable for issue'.
If no batch and the item's kind is medicine → 'Medicine movements require a batch'. Expired and quarantined medicine can therefore never leave stock.
↓
5 · Ensure balance row existsINSERT with quantity = 0 · ON CONFLICT (warehouse_id, item_id, batch_id) DO NOTHING. Uses the UNIQUE NULLS NOT DISTINCT index so a NULL batch still conflicts correctly.
↓
6 · Lock the balanceSELECT quantity … FOR UPDATE — serialises concurrent issues for the same (warehouse, item, batch).
↓
7 · Overspend guardFor issue / wastage / transfer_out: v_balance < p_quantity → 'Insufficient stock' and the whole transaction rolls back.
↓
8 · Apply deltaSingle UPDATE with a CASE: subtract for the three outbound kinds, add otherwise; bump updated_at. CHECK (quantity ≥ 0) is a final structural guarantee.
↓
9 · Append immutable historyINSERT into stock_movements with actor_id = auth.uid(), reason, reference; RETURNING id → the function's result.

Design property: steps 5–9 are one transaction, so stock_balances is always derivable-consistent with stock_movements. Movements are append-only: no client can update or delete a history row, making the ledger an audit trail in itself.

11 · Module flow: Facilities

FacilitiesScreenHospital picked as in §7; only hospital_admin sees create/toggle controls.
↓
Departmentscreate: hospital_id + name + optional code. Constraints UNIQUE(hospital_id, name) and UNIQUE(hospital_id, code). Activate/deactivate via setDepartmentActive.
↓
Warehousescreate: hospital + optional department + name + location; setWarehouseActive for the inverse. warehouses(hospitalId, includeInactive: true) when administering, default active-only when picking a transfer endpoint.

Why UNIQUE(id, hospital_id) is everywhere

Composite uniques on (id, hospital_id) let child tables declare FOREIGN KEY (x_id, hospital_id) REFERENCES parent(id, hospital_id). This makes cross-tenant references structurally impossible: you cannot attach a warehouse from hospital A to a balance in hospital B, even with a crafted request.

Two open loops in this flow

  • approved_quantity exists on the line and is readable, but no UI writes it — approval is a blanket yes/no on the whole request, not a partial allocation.

13 · Module flow: Stock transfers — hrms_transfer_stock

1 · GuardsAuthenticated · quantity > 0 · source ≠ destination ('Choose two different warehouses', backed by CHECK) · role ∈ {hospital_admin, inventory_manager, storekeeper}.
↓
2 · Batch check (stricter than §10)When a batch is supplied the quarantine + expiry test is applied unconditionally — transfers of expired or quarantined stock are always refused. Medicine without a batch → 'Medicine transfers require a valid batch'.
↓
3 · Lock + verify sourceSELECT … FOR UPDATE on the source balance; coalesce(v_qty,0) < p_quantity → 'Insufficient stock at source warehouse'.
↓
4 · Debit sourcequantity = quantity - p_quantity, bump updated_at.
↓
5 · Ensure destination rowINSERT 0 + ON CONFLICT DO NOTHING — needed because the destination balance may not exist yet.
↓
6 · Credit destinationquantity = quantity + p_quantity.
↓
7 · Write BOTH ledger legsTwo-row INSERT into stock_movements: transfer_out at source and transfer_in at destination, same quantity, reason, reference and actor_id. Stock is conserved by construction.
↓
8 · Record the transfer headerINSERT stock_transfers (status defaults 'completed') RETURNING id.

Client listing embeds the two warehouse names through explicit FK disambiguation — source:warehouses!stock_transfers_source_warehouse_id_fkey(name) and destination:warehouses!stock_transfers_destination_warehouse_id_fkey(name) — because a single table holds two FKs to warehouses.

Irreversible by design: stock_transfers is granted only SELECT, INSERT. The 'cancelled' enum value exists but no policy permits UPDATE, so a mistaken transfer can only be corrected by a compensating reverse transfer.

16 · Module flow: Users & roles administration

Whole module is hospital_admin-only in UI, and every one of the three RPCs re-checks that server-side.

List — hrms_list_hospital_users(p_hospital_id)Joins hrms_memberships → auth.users to expose email (normally unreachable to clients). The whole thing is gated: the WHERE includes hrms_has_membership(p_hospital_id, '{hospital_admin}'), so a non-admin gets an empty result, not an error.
↓
Add — hrms_add_member(hospital, email, role, dept)1) admin check → 'Only a hospital administrator can assign memberships'. 2) SELECT id FROM auth.users WHERE lower(email) = lower(trim(p_email)); if none → 'No registered account found for this email'. 3) Look for an identical (user, hospital, department, role) membership; if found just flip is_active = true, else INSERT. Idempotent — re-adding cannot duplicate a role.
↓
Deactivate — hrms_set_membership_active(id, bool)Re-reads the membership's hospital, re-checks admin, then refuses self-deactivation → 'You cannot deactivate your own membership' (anti-lockout). Sets the flag only; never deletes.

Deliberate onboarding order

Public self-registration was removed and membership can only be granted to an already-existing account. So the operational flow is: user signs up through a Supabase-console-created account (or a retained legacy path) → an administrator attaches them to a hospital with a role → HRMS screens unlock. There is no bootstrap mechanism for the first hospital_admin; README assigns that to "a trusted administrative process" (direct SQL).

Note the granularity: memberships are per (hospital, department, role). A user can be pharmacist in one hospital and auditor in another, and HrmsService.hospitals() collapses this into hospital → Set<roles> — which is exactly what the UI consumes. Department-level role separation is flattened away at read time.

Two structural observations

  • No read-only role. auditor and finance_officer are treated as ordinary members for reads, but "member" is p_roles IS NULL — i.e. any role, including healthcare_worker, can read every hospital record: balances, costs, suppliers, requisitions. There is no least-privilege read tier.
  • UI gating is narrower than the DB in several places (e.g. finance_officer may change requisition status but _canCreate does not list them for procurement) — so some permitted actions are unreachable without editing the Dart. The inverse also occurs (§15).

20.2 Approval, versioning, consumption

FlowMechanics
ApprovalsetStatus(id, approved|rejected|archived) + setAvailability(active|inactive|restricted|archived). Trigger notify_on_resource_change informs the uploader.
VersioningaddVersion() uploads to versions/{id}/{n}.{ext}, inserts resource_versions, bumps resources.version. Trigger resource_version_snapshot snapshots the previous state on update. restoreVersion() snapshots current, then repoints the resource (version advances, never rewinds).
View / downloadlog_access RPC writes access_logs, then createSignedUrl(path, 300) — a 5-minute URL. isDownloadable requires a file, approved status, and active/restricted availability.
AuditTrigger audit_resource_changes writes audit_logs (readable only by admin/librarian); AuditScreen and accessLogs() surface both.
DiscoveryResourceQuery: free-text or() over title/description/author, type, category, status (defaults to approved only), favorites, mine.
Analyticscounts(), popularByDownloads(), downloadsPerDay(days: 14) → fl_chart in ReportsScreen; broadcast() sends a system notification to all users.
RolesIndependent 4-value ladder: user → staff → librarian → admin, via profiles.role + helper SQL functions current_role() / is_admin() / is_staff_level() / can_manage_resources(). Not connected to HRMS memberships.

Two authorization models coexist

Legacy RLS decides on profiles.role (global). HRMS RLS decides on hrms_memberships.role (per hospital). A user can simultaneously be a legacy user and an HRMS hospital_admin, or a legacy admin with no hospital access. AppState.isAdmin / canApprove / canUpload read only the legacy field, while every HRMS screen reads only the membership set — so the sidebar, the profile badge and the HRMS buttons can legitimately disagree about who a user is. Unifying these is the largest remaining design task.

HRMS emits no notifications. An approved request, an overdue work order, a low-stock item or an expiring batch never produces a notification row — the realtime pipeline is wired only to the legacy resources triggers. README lists this as unimplemented.
